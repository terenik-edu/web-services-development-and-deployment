# Лабораторна робота 1 – порядок запуску

Дослідження накладних витрат (overhead) при переході від прямого виконання
алгоритму до веб-сервісу і далі до контейнера.

## Підготовка

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Обчислювальне ядро `core.py` не використовує жодної зовнішньої бібліотеки –
залежності потрібні лише веб-сервісу, клієнту-бенчмарку та графікам.

## Етап 1 – пряме виконання

```bash
python3 bench_stage1.py
```

Результати: `results/stage1_raw.csv`, `results/stage1_summary.csv`.

## Етап 2 – локальний веб-сервіс

Термінал 1 – сервіс:

```bash
uvicorn service:app --host 127.0.0.1 --port 8000 --workers 1 --log-level warning
```

- `--workers 1` – один робочий процес, інакше заміри були б нестабільними
  й непорівнюваними з Етапом 3;
- без `--reload` – автоперезавантаження спотворює час;
- `--log-level warning` – вимикає журнал запитів: запис рядка в консоль на
  кожен із 330 запитів додається до виміряного часу. Той самий режим
  використовується в контейнері на Етапі 3.

Термінал 2 – бенчмарк:

```bash
python3 bench_client.py --stage stage2 --url http://127.0.0.1:8000
```

Результати: `results/stage2_raw.csv`, `results/stage2_summary.csv`.

## Етап 3 – веб-сервіс у контейнері Docker

Увесь цикл виконує один скрипт:

```bash
./run_stage3.sh
```

Він робить: збірку образу → запуск контейнера з обмеженнями
(`--cpus=1.0 --memory=512m`, порт `8001`) → очікування `/health` →
прогін бенчмарку → фазу навантаження зі збором `docker stats` →
зупинку й видалення контейнера.

Порт навмисно інший (8001), щоб сервіс Етапу 2 міг працювати одночасно
й не можна було переплутати, який саме заміряється.

Результати: `results/stage3_raw.csv`, `results/stage3_summary.csv`,
`results/stage3_docker_stats.csv`.

**Скріншот живого `docker stats`** для звіту: коли скрипт надрукує
«Фаза навантаження», у другому терміналі виконайте

```bash
docker stats lab1-service
```

Фаза навантаження триває 20 секунд (змінна `LOAD_SECONDS` у скрипті).
Вона потрібна саме для спостереження: сама серія вимірювань триває близько
секунди – менше, ніж один виклик `docker stats --no-stream`. У статистику
ця фаза не входить, вона виконується після збереження результатів.

Окремі кроки вручну, якщо потрібно:

```bash
docker build -t lab1-service .
docker run -d --name lab1-service --cpus=1.0 --memory=512m -p 8001:8000 lab1-service
python3 bench_client.py --stage stage3 --url http://127.0.0.1:8001
docker rm --force lab1-service
```

## Кінцеві точки сервісу

| Метод | Шлях | Призначення |
|---|---|---|
| `POST` | `/compute` | обчислення статистик масиву, повертає власні заміри сервера |
| `GET` | `/health` | перевірка готовності (потрібна для очікування контейнера) |
| `GET` | `/stats` | процесорний час і пікова пам'ять процесу сервісу |

Приклад ручної перевірки:

```bash
curl -s -X POST http://127.0.0.1:8000/compute \
     -H "Content-Type: application/json" \
     -d '{"data": [1, 2, 3, 4, 5]}'
```

## Методичні зауваження до вимірювань

- Клієнт тримає **одне постійне з'єднання** (`requests.Session`), інакше
  в кожен замір потрапляло б встановлення TCP-з'єднання, і результат був би
  про мережу, а не про архітектуру.
- Тіло запиту серіалізується **один раз** поза вимірюваною ділянкою, щоб
  різниця `T_total − T_server_total` означала саме транспорт.
- Обробник `/compute` приймає сирий `Request` і розбирає тіло самостійно:
  модель Pydantic виконала б розбір до входу у функцію, і час десеріалізації
  залишився б невиміряним.
- Перед серією виконується `WARMUP` прогрівальних запитів, вони в статистику
  не входять.
- В образ Docker ставиться скорочений перелік залежностей
  (`requirements-service.txt`): без `matplotlib` і `numpy`, які потрібні лише
  для графіків на хості. Позначку `uvicorn[standard]` збережено – без неї
  сервер працював би на іншому циклі подій (`asyncio` замість `uvloop`),
  і Етапи 2 та 3 стали б непорівнюваними.
- Версія Python в образі (`3.11.9`) збігається з локальною, тому різниця в часі
  між Етапами 2 і 3 не пояснюється різними версіями інтерпретатора.
- Docker на macOS працює всередині Linux-віртуальної машини, тому транспортна
  складова Етапу 3 включає ще й мережу цієї ВМ. Це слід зазначити у звіті:
  на Linux-хості приріст був би меншим.
